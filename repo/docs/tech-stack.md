# Tech Stack

## Summary
Same stack as Abode, plus a dedicated video storage service. TypeScript end to end, so one language and one codebase.

| Layer | Choice | Why |
|---|---|---|
| Framework | Next.js 14+ (App Router) | Already known from Abode; good for landing pages (SEO) and app pages in one project |
| Language | TypeScript | One language across frontend and backend |
| Styling | Tailwind CSS | Fast to build, consistent UI |
| Backend / DB | Convex | Database, server functions, file storage and realtime in one; order status updates live without extra work |
| Auth | Convex Auth | Built in; roles stored on the user record |
| Video storage | Cloudflare R2 | Cheap storage with no egress fees; video is too large and costly for Convex file storage |
| Hosting | Netlify (frontend), Convex cloud (backend) | Same setup as Abode |

## Roles
Three roles, stored as a `role` field on the user: `creator`, `brand`, `admin`. Every Convex query and mutation checks the role before it does anything.

## Video handling
- Creators upload sample videos and deliveries directly from the browser to R2 using presigned upload URLs generated by a Convex action. Video never passes through the app server.
- Convex stores only metadata: file key, size, duration, owner, order ID, status.
- Playback uses signed URLs so deliveries are not public until a brand approves.
- Limits set early: max file size and length, accepted formats (mp4, mov), basic client-side compression guidance for weak connections.
- Optional later: Mux for transcoding and adaptive streaming if playback is slow on mobile data.

## Video access
- The R2 bucket is private. There are no public URLs.
- Each delivery has an `originalKey` and a `previewKey`. At first the preview is the same file, streamed with no download button. In Phase 7 it becomes a lower-quality watermarked copy. Until then, a determined brand could still capture the stream, so the protection is weaker.
- Signed URLs are created only by a Convex action that checks the caller's role and the order status first. They expire after a few minutes.

| Order status | What the brand can access |
|---|---|
| `draft_submitted`, `delivered`, `revision_requested` | Preview, stream only |
| `approved` or `paid_out` (`deliver_to_brand`), `completed` (`both`) | Original, downloadable |
| `disputed` | Preview only |
| `cancelled`, `expired`, `refunded`, `removed_early` | Nothing |

In `post_on_page` orders the creator keeps their own copy, so the brand only needs the preview to approve the draft and never receives the original. Creators can always access their own uploads. Public sample videos on creator profiles are low-resolution and stream-only.

## Payments
Phase 1 (portfolio build): **simulated escrow.** The app keeps a ledger in Convex that moves each order through payment states, but no real money moves. This demonstrates the full flow safely.

Phase 2 (only if it goes real): integrate a local gateway such as bKash or Nagad, or a gateway aggregator, after checking the legal side (Digital Commerce Operation Guidelines 2021) with a lawyer or accountant. Requirements for merchant access need checking at that time.

## Order state machine
Main flow, `post_on_page` orders (the creator posts on their own page):
`draft → awaiting_payment → paid_in_escrow → in_progress → draft_submitted → draft_approved → posted → live_period → completed`
- The brand approves the draft before it goes live. The creator posts from their own copy.
- `posted`: the creator submits the post link and a screenshot, and the brand confirms. The first part of the payment (`upfrontPercent`, default 50) is released, minus the fee.
- `live_period`: the post must stay up for `stayUpDays` (default 14). At the end the creator submits an insights screenshot and the brand confirms. The rest is released and the order is `completed`.
- If the post is taken down during the live period, the order moves to `removed_early` and the remaining held amount goes back to the brand, unless the admin decides otherwise.

Flow for `deliver_to_brand` orders (the video goes to the brand for its own ads):
`draft → awaiting_payment → paid_in_escrow → in_progress → delivered → approved → paid_out`

`both` orders follow the post flow, and the original file is released to the brand when the order is `completed`.

Flow with shipping (product type `keep` or `return_required`):
`paid_in_escrow → awaiting_shipment → shipped → received → in_progress → delivered → ...`
The delivery deadline starts at `received`, not at payment.

Revision loop: `draft_submitted` or `delivered` → `revision_requested` → back again, limited by `maxFreeRevisions`.

Side states: `declined`, `cancelled`, `expired`, `disputed`, `refunded`, `removed_early`.
- `expired`: the creator did not accept within `acceptWindowHours`, or missed the delivery deadline. The brand is refunded in full.
- `disputed`: the brand opens a dispute before approval. All timers pause. The admin resolves it as a refund, a partial refund, or a release to the creator.
- Auto-approve: if the brand does nothing for `autoApproveDays` after a draft or delivery, the order moves to `draft_approved` or `approved`. The same applies to confirming proof at `posted` and at the end of the live period. Reminders go out on day 3 and day 6. An open dispute pauses the timer, and the brand always sees "request changes" and "dispute" beside the countdown.

State changes happen only through Convex mutations that validate the current state and the caller's role. Timers use Convex scheduled functions.

## Config values (never hard-coded)
Kept in one config module: `platformFeePercent` (20), `acceptWindowHours` (48), `autoApproveDays` (7), `maxFreeRevisions` (2), `stayUpDays` (14), `upfrontPercent` (50). The last two are starting guesses to test.

## Brand and creator protections
Refund rules (shown in the terms at checkout):
- Creator never delivers or misses a deadline: full refund.
- Delivered but ignores the brief: the admin decides between a refund and another revision round.
- Brief followed but the brand just dislikes it: funds are released to the creator.
- Post removed during the live period: the remaining held payment goes back to the brand.

Physical products (`productType` on the brief):
- `none` / `reimbursed`: nothing is shipped.
- `keep`: the item is part of the creator's payment and is never returned, whether or not the video is approved.
- `return_required`: only for higher-value items. The item is returned only if the order is cancelled or the creator misses the deadline.
- Ship only after payment and creator acceptance. The brand adds the courier and tracking number; the creator confirms receipt.
- The terms say the platform is a marketplace and is not liable for lost items. Have a lawyer check this wording.

Proof of posting: the creator submits the post link and a screenshot at `posted`, and an insights screenshot at the end of the live period. The brand confirms each, and the admin can spot-check. Automatic checking through the Meta API is out of scope for now, because it needs connected accounts and app review. Screenshots can be edited, so ratings and admin checks matter. Add a reminder for creators to follow each platform's paid-partnership labeling rules (check the current rules).

Creator accountability: taking items or not delivering means suspension. Keep tracking numbers and order records as evidence.

Later (Phase 7): ratings and track record, trust tiers with item-value caps, deposit for `return_required` items, creator verification video, license text.

## Core data model (first sketch)
- `users`: role, name, email, avatar
- `creatorProfiles`: userId, bio, categories, pricePerVideo, sampleVideos, socialAccounts (platform, pageUrl, followerCount, avgViews), approvedByAdmin
- `brandProfiles`: userId, businessName, facebookPageUrl, category
- `briefs`: brandId, title, product, goals, requirements, referenceLinks, templateId, productType (`none`, `reimbursed`, `keep`, `return_required`), declaredValue (integer taka, for shipped items)
- `orders`: briefId, brandId, creatorId, orderType (`post_on_page`, `deliver_to_brand`, `both`), price, platformFee, status, acceptDeadline, deliveryDeadline, autoApproveAt
- `deliveries`: orderId, originalKey (private), previewKey (private), version, notes, createdAt
- `shipments`: orderId, courier, trackingNumber, shippedAt, receivedAt (only for `keep` and `return_required` orders)
- `disputes`: orderId, openedBy, reason, status, resolution, createdAt
- `posts`: orderId, platform, postUrl, postedAt, proofKeys (post screenshot, insights screenshot), liveUntil, status (`live`, `removed_early`, `completed`), brandConfirmedAt
- `revisions`: orderId, deliveryId, feedback, createdAt
- `ledgerEntries`: orderId, type (hold, release, fee, refund), amount, createdAt
- `messages`: orderId, senderId, body, createdAt

## Frontend structure
- Public: landing page, creator directory with filters (category, price, platform, followers), creator profile page with social accounts.
- Brand area: create brief, pick creator, pay, track orders, review deliveries, request changes, approve.
- Creator area: profile and samples, incoming orders, deliver video, earnings.
- Admin area: approve creators, view all orders, resolve disputes, release or refund funds.

## Tooling
- ESLint + Prettier, TypeScript strict mode.
- Zod for validating form input.
- Convex's built-in validators on every function argument.
- Vercel-style preview deploys through Netlify for each branch.

## Not included (on purpose)
- Java / Spring Boot: a separate backend would duplicate what Convex does. Java stays for BRACU coursework and a separate Spring practice project.
- Native mobile apps: the site is mobile-friendly, and a PWA is the next step if needed.
- Real payment processing: simulated until the legal side is checked.
